The user explicitly confirmed that “both sources” means the two cv-refactor pipelines: Adzuna and its collection of remote-job boards. It does not mean Tinder/Bumble or only two job websites. The jev-dating reference supplies the local preference/choice workflow; no dating data or Jev calls belong to this app's current scope.

Fieldwork is a Flutter Android client plus a self-contained Python service. The collectors and configs are copied into `backend/`; the original references are not runtime dependencies. Fetching requires the service; saved jobs and cached results work offline. USB testing uses `adb reverse tcp:8765 tcp:8765`. For untethered use the user chose Tailscale Serve (private tailnet HTTPS to the Mac, not Funnel, decided 2026-10-09); `scripts/serve.sh` runs `caffeinate -is -w` on the service PID so the Mac stays awake only while the service runs. Android permits plain HTTP only for loopback and the emulator host; hosted connections require HTTPS.

The Adzuna keys belong to the `wap-ags` secret store, not cv-refactor. `scripts/serve.sh` resolves the two exact named credentials with `CS_SECRETS_SESSION=wap-ags` through the `code-sessions` CLI (the former `ags`, also `ccs`; plain `cs` cannot see that store), or uses environment values; `JOBS_SECRETS_SESSION` overrides the store. Merely changing directories is unreliable because an inherited CS_SECRETS_SESSION can select a different store. Never put the credential values or the local service access token into handoff files or APKs.

AI ranking (added 2026-10-09) supports Claude Code and Codex, each with a Personal or Work subscription selected in app options. Claude defaults to the saved Agents sidebar account aliases Personal and ERPK/Work; Codex can use separate `JOBS_CODEX_PERSONAL_HOME` and `JOBS_CODEX_WORK_HOME` CLI homes. Never fall back to API-key billing or another subscription. The service strips inherited provider/API credentials and keeps cached verdicts separated by engine, selected subscription, account identity, model, profile and preferences. Codex sessions run with its CLI user config, rules, shell, plugins, hooks and web search disabled; verify any changes preserve this. The user's profile for ranking lives in gitignored `backend/profile.md`, built from the cv-refactor CV without contact details.

App updates (added 2026-10-09) go through the service. Publish only with `scripts/build_apk.sh`: the versionCode is minutes since the epoch, and `artifacts/fieldwork.json` must be published alongside the APK, otherwise `/app` reports no build. MainActivity installs builds with the PackageInstaller session API after checking the SHA-256. The installer's status must go to the non-exported `InstallStatusReceiver`, never the exported launcher activity. A security review flagged that as intent redirection. The receiver checks the session id and accepts only a `CONFIRM_INSTALL` nested intent with grant flags removed. There is no androidx dependency and no Dart plugin. Android closes the app after an update, so the user reopens it.

Applied jobs (added 2026-10-09 at the user's request) live on the service in gitignored `backend/applied.json`, not only on the phone, so every search drops them before Claude ranks. A role counts as applied by id, URL or company+title. The phone's copy is only a cache of the server list. Entries imported from email are company entries (`scope: "company"`). The user chose "whole company" as the default, but on 2026-10-09 asked for exceptions for platforms: Proxify (a talent pool) is `match: badge`, so its roles show last with a badge, and Jobgether (an aggregator) is `match: role`, so only the applied title is hidden. Every other company hides all its roles. The 15 companies imported on 2026-10-09 came from application confirmations dated Oct 2–9; see [[reference-gmail-connector]] for the mailbox.

Application tracking (added 2026-10-09, at the user's request: status history, details, notes plus a follow-up date, email trail, and in-app stats) lives in the same `backend/applied.json` entries; the app computes the stats itself. Before any bulk change to `applied.json`, back it up and dry-run against a temporary service instance with a copy of the file (`JOBS_APPLIED_FILE`, `JOBS_ACCESS_TOKEN`, another `--port`); that dry run caught two migration bugs on 2026-10-09. The October 9, 2026 Gmail sync feature adds a daily, read-only import through Claude Personal on the server. See the daily-sync notes below and `README.md` for setup and live status.

Daily Gmail sync (added 2026-10-09 at the user's request) runs in the service process every 24 hours and catches up after server downtime. Private configuration/state are gitignored `backend/gmail-sync-config.json` and `backend/gmail-sync-state.json*`; state survives restarts and a cross-process lock prevents duplicate model calls. The first sweep looks back 30 days; later sweeps overlap the previous success by two days. It checks the connected Claude account, strips inherited API billing credentials, allows only Gmail search/thread reads and blocks all other tools via a PreToolUse hook. Imports are validated as a whole, matched by known application and exact company/role or thread, deduped by Gmail message ID, merged into existing status history and email trails, and atomically saved with a private pre-import backup. Never infer silence as a rejection; ambiguous/unmatched replies leave the prior list untouched and surface a sync error. Only headers/subjects and classification results are saved; full message bodies are not retained. Authenticated `GET /applied` includes Gmail sync status; `GET /gmail-sync` reports status, while `POST /gmail-sync` and `scripts/sync_gmail.sh` start a check only when due. The user switches the Mac's live Claude login between Personal and Work (ERPK) through the Agents sidebar, and the sync uses that live login. On 2026-10-10 a switch to Work made the first scheduled run fail, and the failure counted as the day's attempt. Since then a login refusal (`LoginError`, raised before any model call) does not count toward the daily schedule and retries every 10 minutes (`retry_at` in the state file).

The Applied tab fetches server analytics once per day on app launch/resume (or while open), caches the fetched timestamp and status on-device, retries network failures at most hourly, and preserves the previous results offline. Manual pull-to-refresh still fetches immediately. Build 29859405 with this UI was published on 2026-10-09. On that date the first scheduled live import was set for 22:25 Europe/Bucharest after the Claude Max limit reset; the initial live check had reached that usage limit, so verify `/gmail-sync` and the first import before assuming Gmail data was refreshed.

The CV the app downloads (added 2026-10-09) lives in gitignored `cv/`, moved from cv-refactor at the user's request. cv-refactor's `latex/build.sh` still writes the rebuilt PDF to `~/Documents/cv-refactor/Bogdan-Gherghina-CV.pdf`, so after a CV rebuild the copy in `cv/` is stale until someone copies the new PDF over. The service serves the newest PDF in `cv/` under its own file name, which is the name recruiters see on uploads.

Applying a CV change for real (done for Draft C on 2026-10-12) takes these steps:
1. Save the current files under cv-refactor's vN convention: `latex/cv.vN.tex/.pdf/.txt` and `plushcv.vN.cls`. v11 is the 9 Oct CV.
2. Copy in the new `cv.tex` and `plushcv.cls` together, and run `latex/build.sh`.
3. Regenerate `latex/cv.png` with `pdftoppm -r 110 -singlefile`.
4. `mv -f` the root PDF into `cv/`. Rename, never rewrite in place, because Acrobat keeps open PDFs mapped.
5. Hand-edit `~/Documents/cv-refactor/Bogdan-Gherghina-CV.txt` to match. It is maintained by hand, not generated, and keeps lines such as the faculty that the one-page PDF drops.
